Add first-class **site management** (the `site` namespace; spec user stories 4, 15) so an operator can explicitly add, remove, and list the sites a node serves instead of relying on implicit MFS side-effects of `deploy`. Sites are auto-discovered from MFS `/sites/*` (how `gateway warming`, IPNS republish, and `status` find them), so the three core verbs manage those MFS entries + their pins over the Kubo RPC seam: **list** enumerates `/sites/*` with each site's current CID (`files/stat`) and, when a same-named keystore key exists, its IPNS id (`key/list`); **remove** issues `files/rm /sites/<name>` FIRST (so the site immediately drops out of warm/republish/status auto-discovery) and THEN `pin/rm <cid>` to unpin the content so storage is reclaimed (the unpin is best-effort: a never-pinned site still removes cleanly, reported as `unpinned:false` rather than throwing); **add** places an already-imported `/ipfs/<cid>` into MFS `/sites/<name>` (mkdir parents / rm old / cp) WITHOUT building or importing a CAR. `add` is a DISTINCT verb, not an alias over `deploy`: it is deploy's MFS-placement step in isolation for exposing an existing CID as a site, and `deploy` is expected to reuse the exported `placeInMfs` helper for that step. Adds a `pinRm` (`pin/rm`) method to the Kubo RPC client (the counterpart to `dag/import --pin-roots`) and a thin `pinnace site <verb>` CLI router. Test-first, driven entirely through the recording mock Kubo API (no live daemon, no shared location).
