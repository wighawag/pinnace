Wire the thin CLIENT-facing `pinnace` CLI over the library core: the v1 verbs `provision` (emit cloud-init), `deploy <dir> <site>` (build one CAR + fan out to every configured node with per-site mode), `install-ci` (emit the CI workflow + report secrets/vars), `status` (per-site report per node), and `derive`/`ipns-id` (print a site's `k51...` IPNS id from master + keyId with NO deploy, so ENS contenthash can be set before the first deploy — user story 22). Each verb stays thin: it parses/validates args, resolves config with precedence arg > env (`ldenv`) > `pinnace.json` (reusing the `config-resolution` core seam, never re-implementing precedence), calls the matching core function, and formats output — no business logic in the CLI. The master secret is env-ONLY (via `resolveMasterSecret`), never read from the file, even as a decoy. Config/env/output and the core functions are injectable through a `RunContext`/`ClientDeps` seam (mirroring the `NodeCommandOps` pattern), so dispatch is unit-tested by stubbing the core and asserting each verb calls the right function with correctly-resolved arguments — without a process and without touching the operator's real environment or config. The same operations remain callable as a TypeScript API through the core (user story 20).
