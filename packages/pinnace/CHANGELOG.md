# pinnace

## 0.3.4

### Patch Changes

- 1e7705d: Fix the true root cause of the fresh-box crash-loop: `ipfs-setup.sh` calls `ipfs --version` as ROOT right after installing Kubo, but cloud-init's `runcmd` provides no `HOME`, and the ipfs binary refuses to run without one (`Error: $HOME is not defined`). Under `set -euo pipefail` that aborted the script at its FIRST ipfs call — before the `ipfs` user, the datadir, and `ipfs init` — so a genuinely fresh box never initialised Kubo and crash-looped (502 through Caddy). The script now exports a default `HOME` up front (`export HOME="${HOME:-/root}"`); the per-user `sudo -u ipfs` calls still override it with the ipfs user's home. A test asserts the export is emitted.
- 1e7705d: Bump the emitted cloud-init's default on-box pinnace version (`DEFAULT_PINNACE_VERSION`) to `0.3.4`, the release that exports a default `HOME` in `ipfs-setup.sh` so the script's root-run ipfs calls do not abort a fresh boot.

## 0.3.3

### Patch Changes

- c891abf: Fix the ROOT cause of the fresh-box Kubo crash-loop: `ipfs-setup.sh` ran `ipfs init` / `ipfs config` via `sudo -u ipfs env IPFS_PATH=…` WITHOUT passing `HOME`. `sudo` does not inherit `HOME`, so `ipfs` aborted with `Error: $HOME is not defined`, which under `set -e` aborted the whole setup script before the datadir/config were created — so a truly fresh box never initialised Kubo and crash-looped. Every `sudo -u ipfs env … ipfs …` call now passes `HOME=/var/lib/ipfs`.

  Also: create the datadir in a `runcmd` step BEFORE the `ipfs.service` is enabled (not via `ExecStartPre`). The removed `ExecStartPre=+install -d /var/lib/ipfs` was a catch-22 — the unit's `ReadWritePaths=/var/lib/ipfs` makes systemd fail namespace setup (`226/NAMESPACE`) when the path is missing, before any `ExecStartPre` (even `+`) can run. Snapshot/invariant tests now assert every `sudo -u ipfs` call carries `HOME` and the datadir is created in `runcmd`.

- c891abf: Bump the emitted cloud-init's default on-box pinnace version (`DEFAULT_PINNACE_VERSION`) to `0.3.3`, the release that fixes the root-cause `$HOME`-not-defined abort in `ipfs-setup.sh` and creates the datadir in `runcmd` before the unit starts.

## 0.3.2

### Patch Changes

- a51c5d7: Fix boot-blocking bugs in the emitted cloud-init found on a fresh Debian 13 box:

  1. **`Provide.Interval` is not settable on Kubo 0.38.1** (`ipfs config` errors "not found / maybe use --json" even WITH `--json`), so setting it aborted `ipfs-setup.sh` under `set -e`, leaving the box half-provisioned. It is optional with a built-in default, so the generator no longer emits it (only `Provide.Strategy` is set).

  2. **The daemon crashed with "denylists: permission denied".** Kubo's nopfs plugin reads `$HOME/.config/ipfs/denylists`; with `HOME` unset in the systemd unit it fell back under `/home/ipfs`, which `ProtectHome=true` hides. Added `Environment=HOME=/var/lib/ipfs` so the lookup stays inside the writable datadir.

  3. **`226/NAMESPACE` crash-loop** when `/var/lib/ipfs` was missing at unit start (the hardened unit's `ReadWritePaths=/var/lib/ipfs` fails namespace setup). Added `ExecStartPre=+/usr/bin/install -d -o ipfs -g ipfs /var/lib/ipfs` to guarantee the datadir before the sandboxed daemon starts.

  Snapshot/invariant tests guard all three.

- a51c5d7: Bump the emitted cloud-init's default on-box pinnace version (`DEFAULT_PINNACE_VERSION`) to `0.3.2`, the release that adds `Environment=HOME=/var/lib/ipfs` to the Kubo unit (fixing the nopfs denylists / ProtectHome crash) and drops the unsettable `Provide.Interval` config line.

## 0.3.0

### Minor Changes

- 31da7cb: Auto-load `.env` / `.env.local` from the cwd at CLI startup via `ldenv`'s `loadEnv()`, so a global `npm install -g pinnace` gets the env-only secrets model with no `pnpm ldenv` dev wrapper.

  - The `pinnace` bin now calls a thin startup shim (`src/cli/startup.ts` `main()`) that runs `loadEnv()` (reads `.env` then `.env.local` from the cwd, `.env.local` overriding, MUTATES `process.env`) BEFORE `run()` reads env. `loadEnv()` does NOT override an already-exported value, so an explicitly exported env var still wins over the file.
  - Effective precedence is now **CLI arg > exported `process.env` > `.env.local` > `.env` > `pinnace.json`** — dotenv slots BELOW exported env and ABOVE the config file, keeping the documented "env > file" rule intact. The master + host tokens stay env-only; `.env.local` is only a file SOURCE for those env vars, never a `pinnace.json` field.
  - `ldenv` is now a runtime `dependency` of the `pinnace` package (a published global install needs it at runtime; it was only a root devDependency before).
  - The pure `run(argv, {env})` path stays hermetic: the `loadEnv()` side effect lives ONLY in the startup shim, so unit tests inject `env` and never read a real `.env`.
  - README (package): documents that the bin auto-loads `.env.local` from the cwd for global users and the effective precedence.

  Tests isolate cwd to a temp fixture dir (with a fixture `.env.local`) and assert its vars reach the resolver, that an exported value wins over the file, that `.env` layers below `.env.local`, that an absent dotenv is a no-op, and that `run()` never reads a real `.env` (only the injected env). Every touched `process.env` key is captured + restored so no test leaks env.

  ## Decisions
  - **The `loadEnv()` call lives in a new bin/startup shim (`src/cli/startup.ts` `main()`), NOT inside `run()`.** `run(argv, {env})` is the hermetically-injected pure path (config resolution reads the injected `env`); putting the one impure, filesystem-touching step (dotenv load) in front of it keeps that path testable without a real cwd/`.env`. Alternative considered: calling `loadEnv()` at the top of `run()` (rejected: it would make every `run()` caller — including unit tests — read a real `.env`, breaking hermeticity). The shim exposes an injectable `loadDotEnv` seam purely so the ordering (loadEnv-before-run) is unit-testable; production always uses the real `ldenv.loadEnv`. Touches: `src/cli/bin.ts` (now calls `main`), the `run()` seam (unchanged, still pure).
  - **CONTEXT.md `config resolution` glossary left as `CLI arg > env (ldenv) > pinnace.json`.** dotenv is not a NEW layer — it is the `ldenv` env layer already named there; `.env.local` / `.env` are just file SOURCES that populate `process.env`, and "already-exported wins" preserves the "env > file" ordering. So this introduces no new domain concept and does not re-mean `env`. The fuller chain (exported > `.env.local` > `.env`) is documented in the package README where operators read it, not in the glossary. Touches: the shared `config resolution` vocabulary (deliberately unchanged).

## 0.2.0

### Minor Changes

- 5383b10: Make the on-box `pinnace` install pinned, reproducible, and boot-safe in the emitted Hetzner cloud-init. The install line now pins the agent (`npm install -g pinnace@${PINNACE_VERSION}`, defaulting to the published `0.1.0`) via a named `DEFAULT_PINNACE_VERSION` knob (overridable per box with `--pinnace-version`), replaces the stale `setup_20.x` NodeSource line with a current LTS via a named `DEFAULT_NODE_MAJOR` (Node 22, overridable with `--node-major`), and hardens first boot: the `ipfs` service user is created by cloud-init's `users:` module (before `runcmd`, so no step can hit "invalid user 'ipfs'"), the dashboard dir is created before the agent install, and `pinnace-setup.sh` is invoked with `|| true` so a transient npm/registry failure can never abort the boot (Kubo, the firewall, and Caddy come up regardless). Snapshot/invariant tests lock the pinned pinnace version, the Node major, and the boot-safe ordering.

  ## Decisions
  - **Pin scheme: `npm install -g pinnace@<DEFAULT_PINNACE_VERSION>` with a named default `0.1.0`, overridable via a `provision` input (`--pinnace-version`).** Mirrors the existing `DEFAULT_KUBO_VERSION` knob so a release bump is one obvious edit and a box boot is reproducible (no floating `latest`). Alternative considered: floating `latest` (rejected: non-reproducible boots, the exact bug this task closes). Touches: the `provision` command's flag surface (adds `--pinnace-version`, `--node-major`, and wires the already-typed `--kubo-version`), and the emitted `PINNACE_VERSION` env value.
  - **Node LTS default = 22 as `DEFAULT_NODE_MAJOR` (was hardcoded `setup_20.x`).** Node 20 is the oldest LTS (EOL ~2026-04) and incoherent with the repo's Node 24 toolchain; 22 is a current active LTS. Kept a named knob (not the repo's Node 24) to stay on an LTS line for a long-lived unattended box, overridable per box. Touches: the emitted NodeSource line + `NODE_MAJOR` env value. Discharges observation `cloud-init-node-major-hardcoded-and-stale.md`.
  - **Boot-safety via `users:` + `|| true` + reordering.** The `ipfs` user moves to cloud-init's `users:` module (runs before `runcmd`); the dashboard `install -d -o ipfs` runs before the agent install; `pinnace-setup.sh` is guarded with `|| true`. This addresses bugs A + B of observation `cloud-init-first-boot-ipfs-user-race-and-set-e-abort.md`. Bug C (cloud-init reporting `done` despite a failed `runcmd`) is a separate surfacing concern, out of this task's scope and left for `cloud-init-generation` follow-up. The mid-`ipfs-setup.sh` `useradd` guard is kept as an idempotent safety net (`if ! id ipfs`).

- 43ad88e: Wire the `pinnace` CLI so every documented verb runs end-to-end (no more validate-and-return-0 stubs), reusing the existing `RunContext`/`ClientDeps` injectable seam (no forked dispatch idiom).

  - **`node <verb>` (on-box):** `runNodeCli` now assembles a `NodeCommandContext` from the box env (`/etc/pinnace-node.env`, exported into the process environment by the systemd timer's `EnvironmentFile`) and invokes `runNodeCommand` (was: return 0). It builds a LOCAL Kubo client (`http://127.0.0.1:5001` + `RPC_BEARER_TOKEN`), reads `role` from `NODE_ROLE`, `sitesDir`/`recordsDir`/`cacheDir`/`dashboardDir` from `SITES_DIR`/`RECORDS_DIR`/`CACHE_DIR`/`DASHBOARD_DIR`, `publisherEndpoint` from `PUBLISHER_ENDPOINT`, and the gateway list from `WARM_GATEWAYS`, and injects the OWNED status op (`makeStatusOp`). A missing `RPC_BEARER_TOKEN` / invalid `NODE_ROLE` is a loud, named error. A live run proved that without this the on-box `republish`/`mirror` timers were no-ops (publisher never populated `/records/`, replica got `no-record`).
  - **`site <verb>`:** `runSiteCli` now assembles a per-host Kubo client (endpoint from resolved config, token env-only via `resolveHostToken`) and invokes `listSites` / `removeSite <id>` / `addSite <id> <cid>` (was: return 0). `--host <name>` selects the node; it may be omitted only when exactly one host is configured.
  - **`status` (on-box):** the production node status path now uses `makeStatusOp` (the real per-site CID/IPNS/announce/gateway report), injected at the `runNodeCli` call site, not the thin `defaultStatus` stand-in.
  - **`promote <id>` (story 14):** a new dispatchable CLI verb that derives the per-site key from the env-only master + the site `id` and invokes `promoteReplicaToPublisher` (import key + flip role) against the chosen host.
  - **cloud-init:** the emitted `/etc/pinnace-node.env` now carries the on-box PATH keys the node verbs read: `DASHBOARD_DIR=/var/www/ipfs-dash`, `RECORDS_DIR=/var/www/ipfs-dash/records` (under the dashboard dir so the publisher's exported record is served at `${DASH_DOMAIN}/records/<id>.ipns-record`, exactly where a replica's mirror fetch looks), and `CACHE_DIR=/var/lib/ipfs/records-cache` (replica fallback cache, under the ipfs user's writable home).

  Dispatch tests (mock/stub the core + the env) assert each verb calls the correct core function with correctly-resolved args and isolate env/config so the operator's real environment/config is untouched.

  ## Decisions
  - **`node` verbs read the on-box `/etc/pinnace-node.env`, NOT the operator's `pinnace.json`.** These verbs run ON a provisioned box via the systemd timer, whose `EnvironmentFile=/etc/pinnace-node.env` exports the box config into the process environment; so `runNodeCli` resolves everything from `RunContext.env` (the same seam the client verbs use), keyed by the exact env names the cloud-init emits (`NODE_ROLE`, `RPC_BEARER_TOKEN`, `SITES_DIR`, `RECORDS_DIR`, `CACHE_DIR`, `DASHBOARD_DIR`, `PUBLISHER_ENDPOINT`, `WARM_GATEWAYS`). Alternative considered: reading `pinnace.json` on the box (rejected: the box has no operator config file; the env file IS the box's config). Touches: the cloud-init env-file keys (this change adds `RECORDS_DIR`/`CACHE_DIR`/`DASHBOARD_DIR` there) and the on-box local-Kubo endpoint (`127.0.0.1:5001`, the localhost-bound RPC the cloud-init configures).
  - **`makeStatusOp` is injected at the production call site (`runNodeCli`), not made the module-level `DEFAULT_OPS.status`.** This satisfies "the production status path uses `makeStatusOp`" while keeping `node-commands.ts`'s default a safe, network-free stand-in for hermetic direct `runNodeCommand` calls (making the module default the live op would push real `delegated-ipfs.dev`/`dweb.link` fetches into any un-injected caller, including that module's own tests). The status-report module doc already anticipates this: "status delegates to the status-report core injected via ctx.ops". Alternative considered: setting `DEFAULT_OPS.status = makeStatusOp()` and updating the node-commands test to inject fakes (rejected: expands scope into another module's test to move a live-network default onto every caller). Touches: `NodeCommandOps.status` seam; the `defaultStatus` doc now states it is the fallback and production injects the owned op.
  - **On-box `CACHE_DIR = /var/lib/ipfs/records-cache`.** The record-sequence ops `mkdir -p` their own dirs, but the timers run as `User=ipfs`, so the cache must sit under a path that user can write; `/var/lib/ipfs` is the ipfs home the cloud-init creates + chowns. `RECORDS_DIR` sits under the already-created+chowned `/var/www/ipfs-dash`. Touches: the emitted cloud-init + the replica fallback path.
  - **Host selection for `site`/`promote`: `--host <name>`, omittable only for a single configured host.** A multi-host config without `--host` is a loud error (never a silent pick). Alternative considered: fan out across all hosts (rejected for `site`/`promote`: these act on ONE node, unlike `deploy`/`status` which are inherently multi-node). Touches: the `--host` flag shared by `site` and `promote`.
  - **`promote <id>` verb surface.** `promote <id> [--host <name>]`: resolves the master env-only (via `resolveMasterSecret`, like `derive`), feeds the single `id` as the KDF input, derives the key (`deriveIpnsKey`), and calls `promoteReplicaToPublisher` with the chosen host's `role` as `currentRole`. This makes story 14 dispatchable, discharging the open question in `work/notes/observations/review-nits-publisher-replica-model-2026-07-24.md` (promote was core-only). Touches: the master env-only surface (shared with `derive`) and the promote/key-import core seam.

- db6bfa6: Add the `install-ci` CI emitter behind a `CIProvider` seam, with GitHub Actions as the first (v1-only) implementation. `emitCi({system, buildCommand, outputDir, ...})` is a PURE core function: it returns the deploy workflow file (path + contents) plus the required repo secrets/vars report, so the CLI wrapper writes the file and prints the report. Other CI systems are Out of Scope but slot in behind the same seam later.
- 56c86a9: Wire the thin CLIENT-facing `pinnace` CLI over the library core: the v1 verbs `provision` (emit cloud-init), `deploy <dir> <site>` (build one CAR + fan out to every configured node with per-site mode), `install-ci` (emit the CI workflow + report secrets/vars), `status` (per-site report per node), and `derive`/`ipns-id` (print a site's `k51...` IPNS id from master + keyId with NO deploy, so ENS contenthash can be set before the first deploy — user story 22). Each verb stays thin: it parses/validates args, resolves config with precedence arg > env (`ldenv`) > `pinnace.json` (reusing the `config-resolution` core seam, never re-implementing precedence), calls the matching core function, and formats output — no business logic in the CLI. The same operations remain callable as a TypeScript API through the core (user story 20).
- 87b6e40: Add a global `--config <path>` flag to the `pinnace` CLI so the config file can live anywhere (e.g. `runbook/pinnace.json`), not just `./pinnace.json`. `--config` is a GLOBAL flag consumed in `run()` before the command and stripped from the per-verb argv (so a verb parser never mis-reads it), threaded into config loading through the existing injectable `RunContext.loadConfigFile` seam (whose signature widens to `(path?: string) => PinnaceConfigFile`). Default behaviour is UNCHANGED: with no `--config`, `./pinnace.json` is read if present and its ABSENCE stays a benign empty config (a config file is optional). But an EXPLICITLY named `--config <path>` that is missing / unreadable / invalid JSON FAILS LOUD (a `ConfigLoadError` naming the path, exit 1) rather than silently resolving to an empty config, because an operator who named a file has claimed it exists and a typo'd path would otherwise surface as confusing downstream "no hosts configured" errors. Precedence is unchanged (CLI arg > env > file); `--config` only chooses WHICH file is the file layer, and no secret gains a file path (master/token stay env-only). Tests drive the flag through the injectable loader and real temp files, isolating the operator's real `./pinnace.json` and real env.
- f24586f: Fix the emitted cloud-init to configure Kubo's `Provide.Strategy` / `Provide.Interval` instead of the deprecated `Reprovider.*` keys, which the pinned Kubo (v0.38.1) FATALs on at startup. Previously a provisioned node crash-looped and never came up; now the emitted config boots cleanly, guarded by a snapshot invariant that forbids any `Reprovider` key.
- 4c210e7: Generate a Kubo node's cloud-init YAML programmatically in TypeScript behind a `HostProvider` seam, with `hetzner` as the first implementation (`provision(input)` returns a ready-to-paste `cloud-init.yaml` from a host/site/role config). Per ADR-0002, the cloud-init does NOT bake the reference's bash loop scripts: it INSTALLS the `pinnace` binary on the box and schedules `pinnace node republish|mirror|warm|status` on role-gated systemd timers, with `NODE_ROLE` written from config so republish/mirror self-gate (all timers safe on every box). Snapshot + invariant tests lock the emitted YAML and the security properties.
- 2d40741: Add config resolution: every setting resolves CLI arg > env (via ldenv) > `pinnace.json`, over a typed schema for hosts (endpoint, token, role, publisherEndpoint) and sites (name, mode, keyId, ensName, sourceDir, optional external key). The master secret is env-only by construction (`resolveMasterSecret` has no file path); a `master` field placed in `pinnace.json` is provably ignored.
- b1cf582: Two config-model corrections in `config-resolution` + its consumers.

  (1) The bearer **token** is now ENV-ONLY by construction, exactly like the master secret: `HostConfig` (the `pinnace.json` host schema) has NO `token` field at all, so a token can never live in the config file (a stray `token` in a file object is ignored, mirroring the master decoy). A host's token resolves ONLY as `CLI > env(PINNACE_HOST_<NAME>_TOKEN)` via the new `resolveHostToken`; an unresolved (or empty) token is a LOUD `MissingHostTokenError` naming the exact env var (e.g. `host 'publisher' has no token; set PINNACE_HOST_PUBLISHER_TOKEN`), never a silent `""` / downstream 401. The failure is LAZY: resolved per host only when an operation (deploy/status) actually builds that host's client, so a configured-but-unused host never blocks unrelated work.

  (2) A site is now identified by ONE value: `id`. Both `name` and `keyId` are removed from `SiteConfig`, replaced by a single `id` used as BOTH the MFS entry (`/sites/<id>`) AND the frozen KDF input (ADR-0001 unchanged; the derivation keeps its internal `keyId` parameter but the config/user surface feeds `id` into it). `SiteConfig` becomes `{ id, mode, sourceDir, ensName?, externalKey? }`; `ensName?` is retained as the optional eth.limo-warming hint (not identity, never a derivation input). The CLI reflects the single id (`deploy <dir> <id>`, `derive <id>`; the `--key-id` flag is removed), and every site-`name` consumer (deploy MFS placement + publish key lookup, status, warm, site-management, node record-sequence, and the operational result/context `name` fields on `DiscoveredSite`/`SiteOutcome`/`SiteStatus`/`SiteListing`/`Remove`/`AddSite`) is renamed to `id`. Because the one `id` is both the MFS entry and the keystore key name, deploy's publish lookup and key-import's import name agree by construction (this SUBSUMES `unify-ipns-key-name-convention`). CONTEXT.md updated: the `keyId`/`ENS name` split is replaced by a single site `id`, `token` is documented as env-only, and `ensName` as the optional eth.limo-warming hint.

- 139da9a: Add the host-agnostic **deploy** core operation (`deploy`; spec user stories 4, 6, 7): build a site's CAR ONCE (via the `car-build` seam), then fan out across every configured node (each with its OWN bearer token) so all nodes serve the IDENTICAL CID with no single point of failure. Per node the flow is `dag/import?pin-roots=true` (import + pin) then MFS placement at `/sites/<name>` (mkdir parents / rm old / cp `/ipfs/<cid>`, reusing the exported `placeInMfs` helper so warm/republish/status auto-discover the site). The per-site **mode branch** is wired here: `ipfs` mode does land+pin+MFS ONLY (no key, no publish), while `ipns` mode ADDS the publish path (`key/list` then `name/publish`) and ONLY on a publisher target whose publish switch is not disabled; a `replica` (or a publish-disabled publisher, the prototype's `PUBLISH_IPNS=0`) lands content but NEVER signs. Deploy assumes the publisher already holds the site key (looked up via `key/list`, imported by the sibling `key-import-publisher` task) and does NOT `key/gen`/`key/import`; if no key exists yet it lands content without signing rather than provisioning one.
