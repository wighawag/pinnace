# pinnace

## 0.1.0

### Minor Changes

- 50d29b2: Add the in-process CAR builder (`buildCar` / `writeCar`): given a site source directory it builds a Content Addressable aRchive whose root is a real UnixFS directory preserving the site structure (`index.html`, `assets/...`), using the `ipfs-car` (`createDirectoryEncoderStream`, `CAREncoderStream`) and `files-from-path` (`filesFromPaths`) libraries entirely in-process — no external CLI, no output scraping. The root CID is captured authoritatively as the LAST block the directory encoder emits and re-encoded into the CAR header, so `dag/import?pin-roots=true` pins the site root. Honors the prototype bug-fix: `filesFromPaths([sourceDir])` already yields site-relative paths, so no leading segment is stripped (the CAR root IS the site dir). Tests decode the built CAR's bytes (never trusting stdout) to assert the root is a UnixFS directory, the structure is preserved with `index.html` at the root, the header root matches the decoded root block, and identical input yields an identical CID. This is the default and primary deploy artifact (spec user stories 4-6).
- db6bfa6: Add the `install-ci` CI emitter behind a `CIProvider` seam, with GitHub Actions as the first (v1-only) implementation. `emitCi({system, buildCommand, outputDir, ...})` is a PURE core function: it returns the deploy workflow file (path + contents) plus the required repo secrets/vars report, so the CLI wrapper writes the file and prints the report. The emitted GitHub Actions workflow ports the reference Action's shape (checkout, setup-node, install, build, a deploy step reading the multi-node env contract, a run summary), with two corrections vs the reference: the deploy step invokes `pinnace deploy` (this tool now owns deploy, no bash/TS drift) and the env carries the multi-node + per-site-mode semantics the deploy core enforces. The report splits `IPFS_TOKEN` (secret, comma-separated tokens, publisher first) from the repo variables `IPFS_API` (comma-separated endpoints, publisher first), `SITE_NAME`, and `SITE_MODE` (ipfs | ipns, default ipns). Multiple nodes serve the same CID; in ipns mode the publisher publishes the signed record and replicas mirror it. Snapshot-locked workflow + a secrets/vars-report assertion. Other CI systems are Out of Scope but slot in behind the same seam later.
- 56c86a9: Wire the thin CLIENT-facing `pinnace` CLI over the library core: the v1 verbs `provision` (emit cloud-init), `deploy <dir> <site>` (build one CAR + fan out to every configured node with per-site mode), `install-ci` (emit the CI workflow + report secrets/vars), `status` (per-site report per node), and `derive`/`ipns-id` (print a site's `k51...` IPNS id from master + keyId with NO deploy, so ENS contenthash can be set before the first deploy — user story 22). Each verb stays thin: it parses/validates args, resolves config with precedence arg > env (`ldenv`) > `pinnace.json` (reusing the `config-resolution` core seam, never re-implementing precedence), calls the matching core function, and formats output — no business logic in the CLI. The master secret is env-ONLY (via `resolveMasterSecret`), never read from the file, even as a decoy. Config/env/output and the core functions are injectable through a `RunContext`/`ClientDeps` seam (mirroring the `NodeCommandOps` pattern), so dispatch is unit-tested by stubbing the core and asserting each verb calls the right function with correctly-resolved arguments — without a process and without touching the operator's real environment or config. The same operations remain callable as a TypeScript API through the core (user story 20).
- 87b6e40: Add a global `--config <path>` flag to the `pinnace` CLI so the config file can live anywhere (e.g. `runbook/pinnace.json`), not just `./pinnace.json`. `--config` is a GLOBAL flag consumed in `run()` before the command and stripped from the per-verb argv (so a verb parser never mis-reads it), threaded into config loading through the existing injectable `RunContext.loadConfigFile` seam (whose signature widens to `(path?: string) => PinnaceConfigFile`). Default behaviour is UNCHANGED: with no `--config`, `./pinnace.json` is read if present and its ABSENCE stays a benign empty config (a config file is optional). But an EXPLICITLY named `--config <path>` that is missing / unreadable / invalid JSON FAILS LOUD (a `ConfigLoadError` naming the path, exit 1) rather than silently resolving to an empty config, because an operator who named a file has claimed it exists and a typo'd path would otherwise surface as confusing downstream "no hosts configured" errors. Precedence is unchanged (CLI arg > env > file); `--config` only chooses WHICH file is the file layer, and no secret gains a file path (master/token stay env-only). Tests drive the flag through the injectable loader and real temp files, isolating the operator's real `./pinnace.json` and real env.
- f24586f: Fix the emitted cloud-init to configure Kubo's `Provide.Strategy` / `Provide.Interval` instead of the deprecated `Reprovider.*` keys, which the pinned Kubo (v0.38.1) FATALs on at startup. Previously a provisioned node crash-looped and never came up; now the emitted config boots cleanly, guarded by a snapshot invariant that forbids any `Reprovider` key.
- 4c210e7: Generate a Kubo node's cloud-init YAML programmatically in TypeScript behind a `HostProvider` seam, with `hetzner` as the first implementation (`provision(input)` returns a ready-to-paste `cloud-init.yaml` from a host/site/role config). This replaces the superseded shell `sed`-template prototype. Only host-specific provisioning lives behind the seam; deploy/publish/status stay host-agnostic (they speak only Kubo RPC), so a new host slots in later without touching them (user story 21). The emitted YAML encodes the hardened-node invariants ported (not copied) from the reference: Kubo as a hardened systemd unit; ufw opens 4001 TCP+UDP + 80/443 but NEVER 5001/8080 raw (API + gateway bound to localhost); discoverability (`Routing.AcceleratedDHTClient` + `Routing.Type auto` + `Reprovider.Interval`/`Strategy`); Caddy HTTPS + bearer API reverse proxy. Per ADR-0002, the cloud-init does NOT bake the reference's bash loop scripts: it INSTALLS the `pinnace` binary on the box and schedules `pinnace node republish|mirror|warm|status` on role-gated systemd timers, with `NODE_ROLE` written from config so republish/mirror self-gate (all timers safe on every box). Snapshot + invariant tests lock the emitted YAML and the security properties.
- 2d40741: Add config resolution: every setting resolves CLI arg > env (via ldenv) > `pinnace.json`, over a typed schema for hosts (endpoint, token, role, publisherEndpoint) and sites (name, mode, keyId, ensName, sourceDir, optional external key). The master secret is env-only by construction (`resolveMasterSecret` has no file path); a `master` field placed in `pinnace.json` is provably ignored.
- b1cf582: Two config-model corrections in `config-resolution` + its consumers.

  (1) The bearer **token** is now ENV-ONLY by construction, exactly like the master secret: `HostConfig` (the `pinnace.json` host schema) has NO `token` field at all, so a token can never live in the config file (a stray `token` in a file object is ignored, mirroring the master decoy). A host's token resolves ONLY as `CLI > env(PINNACE_HOST_<NAME>_TOKEN)` via the new `resolveHostToken`; an unresolved (or empty) token is a LOUD `MissingHostTokenError` naming the exact env var (e.g. `host 'publisher' has no token; set PINNACE_HOST_PUBLISHER_TOKEN`), never a silent `""` / downstream 401. The failure is LAZY: resolved per host only when an operation (deploy/status) actually builds that host's client, so a configured-but-unused host never blocks unrelated work.

  (2) A site is now identified by ONE value: `id`. Both `name` and `keyId` are removed from `SiteConfig`, replaced by a single `id` used as BOTH the MFS entry (`/sites/<id>`) AND the frozen KDF input (ADR-0001 unchanged; the derivation keeps its internal `keyId` parameter but the config/user surface feeds `id` into it). `SiteConfig` becomes `{ id, mode, sourceDir, ensName?, externalKey? }`; `ensName?` is retained as the optional eth.limo-warming hint (not identity, never a derivation input). The CLI reflects the single id (`deploy <dir> <id>`, `derive <id>`; the `--key-id` flag is removed), and every site-`name` consumer (deploy MFS placement + publish key lookup, status, warm, site-management, node record-sequence, and the operational result/context `name` fields on `DiscoveredSite`/`SiteOutcome`/`SiteStatus`/`SiteListing`/`Remove`/`AddSite`) is renamed to `id`. Because the one `id` is both the MFS entry and the keystore key name, deploy's publish lookup and key-import's import name agree by construction (this SUBSUMES `unify-ipns-key-name-convention`). CONTEXT.md updated: the `keyId`/`ENS name` split is replaced by a single site `id`, `token` is documented as env-only, and `ensName` as the optional eth.limo-warming hint.

- 139da9a: Add the host-agnostic **deploy** core operation (`deploy`; spec user stories 4, 6, 7): build a site's CAR ONCE (via the `car-build` seam), then fan out across every configured node (each with its OWN bearer token) so all nodes serve the IDENTICAL CID with no single point of failure. Per node the flow is `dag/import?pin-roots=true` (import + pin) then MFS placement at `/sites/<name>` (mkdir parents / rm old / cp `/ipfs/<cid>`, reusing the exported `placeInMfs` helper so warm/republish/status auto-discover the site). The per-site **mode branch** is wired here: `ipfs` mode does land+pin+MFS ONLY (no key, no publish), while `ipns` mode ADDS the publish path (`key/list` then `name/publish`) and ONLY on a publisher target whose publish switch is not disabled; a `replica` (or a publish-disabled publisher, the prototype's `PUBLISH_IPNS=0`) lands content but NEVER signs. Deploy assumes the publisher already holds the site key (looked up via `key/list`, imported by the sibling `key-import-publisher` task) and does NOT `key/gen`/`key/import`; if no key exists yet it lands content without signing rather than provisioning one. Fan-out mirrors the reference prototype's `Promise.allSettled` semantics: a node that fails is reported per-node (`DeployResult.failed`) without sinking the others, and a non-empty subset succeeding is still an overall `success` (some-nodes-up). Behaviour ported (not copied) from `~/searches/ipfs-hetzner/deploy-car.mjs`. Test-first, driven entirely through the recording mock Kubo API (each node its own baseUrl + token + recorded requests, no live daemon): assertions pin the exact per-mode call SEQUENCE for both modes, the same-CAR/same-CID multi-target fan-out with per-token isolation, that a replica never publishes, and the partial-failure-is-still-success behaviour.
- 1cbc1a3: Add the frozen master-key -> per-site IPNS key derivation (`deriveIpnsKey` / `deriveIpnsId`): `HKDF-SHA256(master, info = "pinnace:ipns:v1:" + keyId, 32)` -> ed25519 seed -> `k51...` IPNS id, with the ENS name deliberately never an input. `deriveIpnsId` is the no-deploy/no-network derive-and-print path (user story 22, set the ENS contenthash before the first deploy). Golden-vector tests pin the fixed (master, keyId) -> fixed seed/pubkey/id and assert keyId independence from the ENS name, and ADR-0001 records the frozen scheme (KDF, the exact `pinnace:ipns:v1:` info prefix carrying the version, the empty-salt default, keyId-as-info source, and the ed25519-from-32-bytes step) and why it must never change once names are live.
- 71eac2d: Import the derived per-site IPNS key into the PUBLISHER node's keystore (`serializeIpnsKeyForImport` / `importIpnsKeyIntoPublisher`). The derived ed25519 keypair is serialized into the `libp2p-protobuf-cleartext` `PrivateKey` form `ipfs key import` expects (`0x08 0x01 0x12 0x40` + the 64-byte seed||pubkey `Data`) and POSTed via Kubo `key/import` under the site key name. Import is publisher-only: a `replica` import is REFUSED (`KeyImportRoleError`) with no RPC issued at all, so replicas stay keyless. The client supplies key MATERIAL only; the node signs IPNS records itself via `name/publish` (a separate concern). Tests at the mock Kubo RPC seam pin the serialized bytes (from the golden-vector key), assert the key lands via `key/import` on the publisher with the bearer token, that a replica is refused touching the node not at all, and that the import path issues ONLY `key/import` (no `name/publish`/`routing/put`) and reaches for no client-side signing primitive. ADR-0003 records the load-bearing invariant that client-side key derivation is NOT client-side record signing (spec Out of Scope C-1): the client hands over material, the node is the sole record signer and sequence-number writer.
- f24586f: Fix `KuboRpcClient` file uploads to use `multipart/form-data` (via `FormData`) for `dag/import`, `add`, and `key/import`, matching Kubo's real HTTP contract. Previously these sent a raw `application/octet-stream` body, which real Kubo rejects with `400 file argument 'path' is required` (so `deploy` could not import a CAR against a live node). The mock now enforces the multipart contract so the regression is caught without a live daemon.
- f24586f: Fix `KuboRpcClient.routingPut` to send the signed IPNS record as a `multipart/form-data` file part named `value-file` (the field Kubo requires), completing the multipart-upload fix. Previously it sent a raw body, which real Kubo rejects with `400 file argument 'value-file' is required` (so a replica could not `routing/put` re-announce a record against a live node).
- f647e3f: Add a typed per-node Kubo RPC client (`KuboRpcClient`) wrapping `POST /api/v0/...` with `Authorization: Bearer <token>`, covering `add`, `dag/import?pin-roots=true`, `files/{mkdir,rm,cp,ls,stat}`, `key/{list,gen,import}`, `name/publish`, `routing/{get,put}`, `id`. Non-2xx responses raise a loud `KuboRpcError` naming the endpoint + status. Ships a recording `MockKuboApi` fixture (the primary test seam sibling operations reuse), so all behaviour is proven over HTTP with no Kubo binary.
- 7b9ee5a: Add the on-box `pinnace node <verb>` command surface (`republish`, `mirror`, `warm`, `status`): the recurring loop the same `pinnace` binary runs ON a Kubo node under cloud-init systemd timers, each a thin wrapper over core logic against the LOCAL Kubo RPC. Sites auto-discover from MFS `/sites/*`; `republish` (publisher) and `mirror` (replica) self-gate on `NODE_ROLE` (a wrong-role verb is a clean no-op that touches no Kubo RPC, so scheduling all timers on every box is safe); `warm` re-fetches each CID through the configured gateways and `.eth` names via eth.limo; `status` reuses the `status-report` core logic and writes the dashboard JSON. The record sequence (`publisher-replica-model`) and the per-site status checks (`status-report`) are injectable core ops behind the same seam; this task ships the command surface, role-gating, `warm`, and thin defaults. ADR-0002 records the boundary: Kubo owns pinning (`dag/import --pin-roots`) + provider-record freshness (`Reprovider.Interval`); pinnace's on-box loop owns only IPNS republish/export + mirror/fallback + warm + status; the client CLI and the on-box agent are ONE binary.
- d00c19a: Add the publisher / keyless-replica IPNS record machinery (spec C-2 model; user stories 12, 13, 14) as a dedicated core module (`src/publisher/record-sequence.ts`), so a shared IPNS name stays reachable with a grace window even if the publisher dies. Exactly ONE publisher per name refreshes the record's validity by re-SIGNING it (`name/publish`, ~72h lifetime / ~1h ttl) and EXPORTS the raw signed record (`routing/get`) plus its ipns id to a records dir (`republishAndExport`). Keyless REPLICAS fetch the publisher's exported record, re-announce it (`routing/put`), and FALL BACK to their last cached record when the publisher endpoint is unreachable (`mirrorAndReannounce`) — they NEVER sign (no `name/publish`), upholding the "no client-side record signing" invariant (spec Out of Scope C-1, ADR-0003). The record sequence has a SINGLE implementation (ADR-0002): the on-box `pinnace node republish|mirror` verbs delegate to this core through their `NodeCommandOps` seam via `makeRepublishOp`/`makeMirrorOp` (mirroring how `status-report` supplies the `status` op), so client and box run the same code with no bash/TS drift. `promoteReplicaToPublisher` (story 14) recovers a name without content downtime by reusing the `key-import-publisher` seam to import the derived key and flip the role to publisher, within the record's validity window. Behaviour ported (not copied) from the reference cloud-init scripts `ipfs-ipns-publish.sh` / `ipfs-ipns-mirror.sh`. Proven mock-green at the mock Kubo RPC boundary + a fake publisher endpoint (the full export -> fetch -> `routing/put` -> fallback-to-cache sequence, plus replica-never-signs); a self-skipping live failover smoke test (`record-sequence.live.test.ts`) is shipped opt-in via env for the `verify-ipns-failover-live` follow-up task and touches no real infra by default.

- 62f4a89: Add first-class **site management** (the `site` namespace; spec user stories 4, 15) so an operator can explicitly add, remove, and list the sites a node serves instead of relying on implicit MFS side-effects of `deploy`. Sites are auto-discovered from MFS `/sites/*` (how `gateway warming`, IPNS republish, and `status` find them), so the three core verbs manage those MFS entries + their pins over the Kubo RPC seam: **list** enumerates `/sites/*` with each site's current CID (`files/stat`) and, when a same-named keystore key exists, its IPNS id (`key/list`); **remove** issues `files/rm /sites/<name>` FIRST (so the site immediately drops out of warm/republish/status auto-discovery) and THEN `pin/rm <cid>` to unpin the content so storage is reclaimed (the unpin is best-effort: a never-pinned site still removes cleanly, reported as `unpinned:false` rather than throwing); **add** places an already-imported `/ipfs/<cid>` into MFS `/sites/<name>` (mkdir parents / rm old / cp) WITHOUT building or importing a CAR. `add` is a DISTINCT verb, not an alias over `deploy`: it is deploy's MFS-placement step in isolation for exposing an existing CID as a site, and `deploy` is expected to reuse the exported `placeInMfs` helper for that step. Adds a `pinRm` (`pin/rm`) method to the Kubo RPC client (the counterpart to `dag/import --pin-roots`) and a thin `pinnace site <verb>` CLI router. Test-first, driven entirely through the recording mock Kubo API (no live daemon, no shared location).
- e47e5c4: Add the `status` core operation (spec user story 18): pinnace's discoverability verification surface. For every site auto-discovered from MFS `/sites/*` (over the Kubo RPC seam) it reports four fields so an operator can confirm a deploy landed everywhere: the current CID (`files/stat`), the IPNS id (from `key/list` if a same-named key exists, else absent for ipfs-mode sites), whether the NETWORK announces this node for the CID (an external delegated-routing providers lookup at `delegated-ipfs.dev` whose `.Providers[].ID` list contains this node's PeerID from `id`), and whether a COLD public gateway serves it (a `dweb.link` range-request HTTP probe). The two external checks are INJECTABLE (`ProvidersLookup`, `GatewayProbe`) so tests run against a fake HTTP layer and never the live network; production supplies `fetch`-backed defaults. Both checks fail SOFT: a routing error reports `announced=false` and a gateway error reports `gatewayServes=false`, never a throw, so one flaky endpoint cannot fail the whole report. `makeStatusOp` adapts this core into the on-box `node status` verb's injectable `NodeCommandOps.status` seam. The check shapes are ported (not copied) from the reference prototype `status.sh`. Tested entirely against the mock Kubo API plus the two injected fakes.
