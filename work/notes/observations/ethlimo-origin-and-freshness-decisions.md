---
title: decisions taken adding the eth.limo origin + freshness axes to `status`
date: 2026-07-27
status: open
---

Recorded while building `ethlimo-origin-and-freshness-mismatch` (spec `sites-metadata-in-mfs`). Each is a choice a reviewer or a later task could reasonably want to reverse, so it is written down rather than buried in the diff. It continues `work/notes/observations/ethlimo-probe-and-warm-outcome-decisions.md`, which recorded the same class of choice for the probe itself.

**1. `GatewayProbe` returns a RESULT OBJECT (`{status, headers?}`), not a status number.** The task allowed widening the one probe seam rather than forking it, and the two new axes need the headers the probe already receives. The alternative rejected: a union return (`number | GatewayProbeResult`) that would have spared every existing fake a change but left ONE seam with TWO shapes, which every reader and every future fake then has to normalise. Cost: a second signature change to an EXPORTED type (`GatewayProbe`, `defaultGatewayProbe`) that a library consumer injecting its own probe must follow, one release after the first. Touches: `src/status/status-report.ts`, its tests, and any external injector.

**2. The changeset is a `minor`, not a `patch`.** The previous widening of this same exported type shipped as a patch, and the Gate-2 review nit for that task explicitly asked whether that was the intended semver for an exported-type break (`work/notes/observations/review-nits-ethlimo-warming-status-visible-and-honest-2026-07-27.md`). This one answers it: an exported type whose shape changes is a minor, even pre-1.0. Reversible by editing the changeset before release.

**3. The headers are handed over WHOLE, not filtered by the probe.** `defaultGatewayProbe` copies every response header (lower-cased) into the result; the two header NAMES are spelled only in `src/status/ethlimo-resolution.ts`, which is the module that interprets them. Alternative rejected: a `{ipfsPath, ipfsRoots}` result shape, which would put the wire-format knowledge in the probe and leave the header-name mapping untestable without a live gateway. Consequence: fakes may pass the exact live header pair, and the classifier is tested against the real spelling.

**4. `origin` has a FOURTH state, `frozen`, and it applies to ANY `/ipfs/<cid>` under a name-publishing site.** The task asked for the sub-case (an `ipns`-mode site whose ENS holds an immutable cid never tracks deploys) to be surfaced distinctly, noting it could be read as an `ours`-but-frozen or as a `foreign`. Chosen: `origin` judges only what KIND of thing the ENS record points at and whether it is our identity, so a name-publishing site whose path is `/ipfs/<anything>` is `frozen` (naming the cid); whether that cid is OURS is the `freshness` axis' question, and it answers it right beside. The alternative (`frozen` only when the cid matches, `foreign` otherwise) folds a freshness comparison into the origin axis, which is exactly the collapsing the task forbids. Consequence: a site frozen at somebody ELSE's cid reads `frozen` + `stale (<their cid>)` rather than `foreign`; both facts are on the line.

**5. The word `frozen`.** New vocabulary, checked against the CONTEXT.md glossary: it re-means nothing (`pin` is custody of a CID, `mode` is the publish mode, `ipfs`-mode already means "addressed by cid"). It names the property the operator must act on: the ENS record cannot move. Recorded in the glossary as part of the `origin / freshness` entry so the next author cannot re-fork it.

**6. `foreign` is the ONLY new state rendered as the red negative.** `stale` and `frozen` render in a new neutral-attention style (`.warn` on the dashboard, an unadorned token on the CLI), because post-deploy propagation lag is normal and a frozen record is valid today. Consequence worth knowing: for an `ipfs`-mode site, a `foreign` cid may simply be an OLDER cid of the operator's own (an `ipfs` contenthash must be repointed per deploy), and from outside there is no way to tell that from another site's cid. Said plainly in the module docs.

**7. Cids are compared as STRINGS.** `bafy...` from `files/stat` against `bafy...` from the gateway. A different ENCODING of the same cid (v0 `Qm...` vs v1 base32) therefore reads as `stale`, not `current`. Parsing cids properly would mean taking `multiformats` as a direct dependency for one comparison; deliberately not done, and it is one more reason `stale` is an attention state rather than an accusation. Reversible if a real box ever shows the false positive.

**8. `shortReason` is now EXPORTED from `check-outcome.ts`.** The new axes carry `unknown` reasons that are not `CheckOutcome`s, and they must normalise reasons the same way (one short line, never empty). Alternative rejected: a second private normaliser in the new module, which would drift. `check-outcome.ts` stays a pure leaf.

**9. A mode-less site is read the way `republish` reads it.** For `origin`, a site that stores no `mode` but whose id this node holds a key for counts as publishing a name (so an `/ipfs/<cid>` ENS record reads `frozen`), matching `src/publisher/record-sequence.ts` — the one place in pinnace where an absent mode is NOT the `ipfs` default. Also: a site that WANTS a name but whose IPNS id this node does not know (a replica, or a publisher without the key) reports `unknown`, never `foreign`; a replica therefore reports `unknown` origin for every ipns site it holds, which is honest rather than alarming.

**10. The roll-up token `status: 'ok' | 'unverified'` still ignores all of this.** Unchanged from decision 4 of the earlier note: a `foreign` origin or a `stale` cid does NOT flip a site to `unverified`, because that token has meant "announced AND served" to existing `status.json` consumers. A consumer that wants the mismatch must read `ethLimoOrigin` / `ethLimoFreshness`. Ratify or reverse deliberately, not as a side effect.
