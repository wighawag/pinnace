Recorded while building `show-inferred-ens-name-not-none` (spec `sites-metadata-in-mfs`). Each is a choice a reviewer or another task could reasonably want to reverse, so it is written down rather than buried in the diff.

**1. The four-state classification is CONSOLIDATED into a new sibling module, `src/status/ens-name-display.ts`.** The task invited consolidation "if it is clean". The two renderers had the same three-branch logic written out twice, which is exactly how they came to describe the wrong thing (the STORED field) in unison, so the classification is now shared and each renderer keeps only its own wording/markup: `ensNameDisplay(site) -> {stored|inferred|opted-out|none}`, and no CLI formatting leaks into the HTML view or vice versa. Alternatives considered: (a) putting the classifier in `site/site-wrapper.ts` beside `resolveEnsNameToWarm`, rejected because it would drag a presentation concern into the module that owns storage + the warm rule, and would couple the dashboard to the site/storage layer; (b) leaving the two renderers separate with a cross-reference comment, rejected because the comment is exactly what would drift next time. It is NOT exported from `index.ts`: it is an internal display helper, not new public API. Touches: `cli/run.ts` (`printedEnsName`) and `status/status-html.ts` (`renderSiteRow`).

**2. `status-html.ts` now has ONE import, which softens the "pure, import-free view" phrasing in `ethlimo-probe-and-warm-outcome-decisions.md` (decision 2).** That earlier decision's REASONS were: no import cycle (`node-commands` <-> `status-report`), and the renderer must URI-encode names into `href`s itself. Both still hold: `ens-name-display.ts` is a leaf with no imports of its own, no cycle is possible, and `status-html.ts` keeps its own `ETH_LIMO_HOST` and its own link building. What changed is only the literal "import-free" claim, and the property that actually matters — the renderer RESOLVES nothing and depends on no core — is preserved (the classifier re-applies no rule; it reads the two fields the report already put on the row, and a `.eth` id the report did not resolve still renders `none`, asserted by a test). A reviewer who wants the letter of the old decision back would have to accept the duplicated branch logic this task exists to remove.

**3. User-visible wording: `(inferred)`, in both renderers.** CONTEXT.md already says an absent `ensName` "INFERS the name from a `.eth` id", so `inferred` re-means nothing. The CLI prints `ensName ronan.eth (inferred)`, so that ONE field's value now contains a space (the line is human-oriented; `status.json` is the machine surface and is untouched). The dashboard prints the name in `<code>` plus a muted `<span class="inferred">(inferred)</span>`; `.inferred` is a NEW css class sharing the existing muted colour rule with `.none`/`.empty`, rather than reusing `.none` (which would re-mean "none") or styling an inferred name identically to a stored one (they are not the same thing: an inferred name FOLLOWS the id, a stored one OVERRIDES it). The word is spelled once per renderer rather than shared as a constant, since each medium owns its own vocabulary; both spellings are asserted by tests.

**4. The genuinely-none case keeps its EXISTING tokens (`unset` on the CLI, `none` on the dashboard).** They already differ between the two renderers, and unifying them would be a separate, gratuitously breaking change to two shipped surfaces; this task only removes the case where those tokens were WRONG. Same for `opted-out` / `opted out`.
