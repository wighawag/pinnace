---
title: decisions taken three-stating the status checks (yes / no / unknown-with-reason)
date: 2026-07-27
status: open
---

Recorded while building `unavailable-check-reports-unknown` (spec `sites-metadata-in-mfs`). Each is a choice a reviewer or another task could reasonably want to reverse, so it is written down rather than buried in the diff.

**1. The three states are a shared VOCABULARY module, `src/status/check-outcome.ts`, not three local fixes.** The task exists because this is the FIFTH instance of the defect class, so the fix is a named concept every layer imports: `CheckOutcome = {state:'yes'} | {state:'no'} | {state:'unknown', reason}`, plus `checkAnswer`/`checkUnknown`/`isYes`/`checkState`/`unavailableReason`/`CheckUnavailableError`. It is a pure LEAF (no imports), which is what lets `status-html.ts` use it without importing a core (`node-commands` imports `status-html`, and `status-report` imports `node-commands`, so any core import there would cycle) — the same shape as the existing `ens-name-display.ts`. Alternative rejected: keeping booleans and adding a companion `announcedUnknownReason?: string`, which leaves `announced: false` meaning two things and relies on every renderer remembering to look at the second field. The union makes the compiler force the third case at every consumer, which is the point. New public API: exported from `index.ts`, because it is now part of the report SHAPE, not an internal helper.

**2. The report shape (and `status.json`) is BREAKING: `announced`/`gatewayServes`/`ethLimoServes` are objects, not booleans.** There is no way to carry three states plus a reason in a boolean, and the task requires the JSON payload to carry all three. The alternative considered was a flat pair per check (`announced: 'yes'|'no'|'unknown'` + `announcedReason?: string`), rejected because it doubles the keys and lets a reason drift away from the value it explains. Consequence: a machine consumer of `status.json` reading `announced === true` must move to `announced.state === 'yes'`; `gatewayHttp`/`ethLimoHttp` are untouched. Shipped as a `minor` (0.x) with the break spelled out in the changeset. This contradicts nothing earlier: `ethlimo-probe-and-warm-outcome-decisions.md` (decision 3) chose a three-valued OPTIONAL boolean for `ethLimoServes`; that shape survives as the OUTER optionality (absent = not applicable), with the boolean replaced by the outcome. Four states now: `yes` / `no` / `unknown` / absent.

**3. A gateway that ANSWERS a non-2xx is a real `no`; only an unmakeable probe is `unknown`.** A cold 504 or a 404 from `dweb.link`/`<name>.limo` is the gateway telling us it does not serve the content, which is exactly the negative the column exists to report; the task's own wording ("distinct from a gateway that answered and did not serve") says so. Deliberately accepted grey area: a `429` from a GATEWAY is counted as a `no` even though it is arguably "could not check". Reversing that is a one-line predicate change if a real box shows it mattering, but inventing a per-status policy now would be guesswork, and it would also diverge from the `warm` side (`node-commands.ts#safeWarm`), which counts any non-2xx as a warm that did not warm. The DELEGATED-ROUTING lookup is the opposite case and is handled the other way (any non-2xx is `unknown`), because there the non-2xx is the ROUTER refusing to answer the question, not an answer.

**4. `!peerId` reports `unknown ("no peer id")` AND skips the lookup entirely.** We could not identify the node, so there is nothing to look for; asking anyway would spend a rate-limited request to learn nothing. It is not a site-level failure and never reads as one.

**5. An ABSENT verdict now renders as `unknown`, not `no` (dashboard).** `SiteOutcome.announced`/`gatewayServes` are optional (other verbs, and the thin on-box `defaultStatus` stand-in, fill neither), and the old `indicator()` painted `undefined` as the red `no` — the same lie, from a report that ran no check at all. `checkState(undefined) === 'unknown'` makes that honest. It changes the dashboard for the thin stand-in path (previously two red crosses per site, now two neutral `unknown`s). NOTE this is the ONE place absence means "unknown" while for `ethLimoServes` absence means NOT APPLICABLE; they do not collide because the eth.limo cell decides on `ensNameToWarm` (no name => the cell shows `none` and no verdict is consulted), and both are documented at their fields.

**6. User-visible wording keeps the existing tokens and adds one.** CLI: `true`/`false` unchanged for a check that RAN, `unknown (<reason>)` added, `n/a` unchanged for not-applicable. Dashboard: `ok`/`no` unchanged, `unknown (<reason>)` added in a new muted `.unknown` CSS class that joins the existing `.none, .empty, .inferred` colour rule (neutral, never the red `.no`). Reasons are normalised to ONE short line (whitespace collapsed, truncated at 120 chars, empty => `could not check`) because they land in a status line and a table cell, and are HTML-escaped like every other report string.

**7. The `ok`/`unverified` roll-up treats `unknown` as `unverified`.** Only a definite yes on BOTH CID checks is `ok`. No new roll-up token was introduced: `unverified` already means "not confirmed", which is precisely the state an unknown leaves a site in, and adding a third token would re-open decision 4 of `ethlimo-probe-and-warm-outcome-decisions.md` (which deliberately froze what that field means).
